# AGENTS.md

Guidance for coding agents (pi, Codex, …) working with code in this repository.

## What this is

Syneva is a CLI (`syneva`) whose `start` command runs the **hub**: one long-running process per machine that hosts review desks (one per repo + session, each a browser UI over a git diff, a file or a PR) and serves a dashboard over them. A human reviews (accept/reject changes, comment, ask questions), and a coding agent opens desks on the hub (`syneva open`, which starts a hub when none runs) and attaches to them via CLI subcommands to receive the review, reply, and re-diff its edits into the open tab. Agents never run a server. No model runs inside Syneva — it is a protocol + interface only.

Product positioning lives in `PRODUCT.md`, the review app's UI design language in `DESIGN.md` (the public site's in `apps/landing/DESIGN.md`) — read them before product or design decisions.

## Landing deploy

The landing (`apps/landing`, an Astro app) deploys to Cloudflare Workers through CI only, never from a local machine: its pages as static assets, and one on-demand route (the launch list signup) in the Worker, bound to a D1 database, a rate limiter and the `RESEND_API_KEY` secret (from the `syneva` Infisical project, `dev` and `prod`, synced into the Worker on every deploy; GitHub holds no secret). Config lives in `nextnode.toml`; the pipeline is `NextNodeSolutions/core`'s `deploy.yml`, which also applies the D1 migrations before each deploy: `deploy-dev.yml` fires on merge to `main` (dev.syneva.dev), `deploy-prod.yml` is a manual dispatch (syneva.dev, gated on the dev pipeline). Its build output, the Worker's types and local bindings, and the pipeline's smoke check: `apps/landing/AGENTS.md`.

## Commands

Every command is a pnpm script in `package.json` — that file is the authoritative list (`dev`, `build`, `check`, `lint`, `lint:types`, `lint:fix`, `format`, `format:check`, `perf-smoke`, `release`). CI (`.github/workflows/ci.yml`) runs the same gates on Node 24 for every pull request, stacked ones included — all must pass. The tooling needs Node 24 (`devEngines`); the published CLI keeps its `engines.node >= 22` contract.

## Test layout

No unit-test suite at the moment: the colocated `*.test.ts` suite was removed and a replacement suite is planned — do not invent tests for a change unless asked. `test/` holds the frontend perf benchmarks (below) and the end-to-end conformance checks of the hub's stream (`test/stream`) and of its probe (`test/bridge`); future e2e suites join the same folder.

## Benchmarks

The perf timeline is tracked data, not a chat log: after a render-path change, measure the cold open (headless, via `pi-frontend-check`) and record the run with `node test/benchmarks/bench-dashboard.mjs --record <file>`, then `--check`. Read `test/benchmarks/README.md` for the run shape and `test/benchmarks/AGENTS.md` for the rules that keep runs comparable.

## Workspace layout

The repo is a pnpm + Turborepo workspace. The publishable package is `apps/syneva` (the `syneva` npm/pi package: bin, `files`, the `pi` key, `prepack`); the build units live in `packages/`, the public site in `apps/landing`:

- `packages/contracts` (`@syneva/contracts`) — the shared wire shapes, no dependencies, compiled by `tsc` to its own `dist/` (ESM + `.d.ts`); core, local, the frontend and the landing import it through `@syneva/contracts/*` specifiers.
- `packages/core` (`@syneva/core`) — the engine: the review domain, the application use cases, the hub and its routes on the Fetch API, over ports (`application/ports.ts`) the platform implements. `GitPort` is sized to what GitHub's API serves: its base reads a repository at two refs, while the working tree (`workingTree`) and writing the index (`staging`) are optional capabilities a use case asks for (`application/capabilities.ts`; a desk's state tells the tab as `capabilities`), and a PR number or URL resolves through the optional `PullRequestPort` — local wires them all, over git and `gh`. It runs under node:http today and is meant to run in the user's Durable Object too (`docs/rfc/0001-core-web-local.md`, 3.1), so it is Workers-clean and timer-free: no Node module but `node:path` and `node:crypto` (both in `nodejs_compat`), no Node global (`process`, `Buffer`, `__dirname`, `require`), no timer (a grace period or a TTL is a deadline compared on the next read, as the hub's closed-desk grace in `hub/hub-desks.ts`), and no workspace import but `@syneva/contracts`. Two gates hold it: oxlint (the `packages/core/src` overrides in `oxlint.config.ts`, with the RFC section each ban protects) and its `check`, which runs `tsc` twice, under Node and then under `tsconfig.workers.json` (ES2024 and the WebWorker libs, no `@types/node`, and of Node only what `types/node-compat.d.ts` declares), so a `process`, a `Buffer` or a `node:fs` import fails the type-check even if lint missed it.
- `packages/local` (`@syneva/local`) — the Node side: the outbound adapters (git, the filesystem, the oxc parser, the editor, the package registry, the console, the probe to the web's bridge), node:http under core's router, the CLI, the pi bridge and the composition roots that hand core its ports. It imports core and contracts, never the browser world. The published package BUNDLES it: `apps/syneva/scripts/build-dist.mjs` runs tsdown over local's `bootstrap/cli.ts` and `adapters/inbound/pi/pi-bridge.ts` into `apps/syneva/dist/cli.js` / `dist/pi-bridge.js` (core and contracts inlined from their built `dist/`, harness peers `@earendil-works/pi-coding-agent` and `typebox` external) and copies the built UI next to them. `dist/cli.js` is the published bin.
- `packages/frontend` (`@syneva/frontend`) — the browser frontend, React 19 bundled by Vite from two entries: `src/app/main.tsx` (the desk, `ui.js`, served under `/d/<id>/`) and `src/app/dashboard.tsx` (the hub dashboard, `dashboard.js`, served at every dashboard path: `/`, `/reviews`, `/projects` and `/projects/<projectId>`, `/plans` and `/plans/<planId>`, `/settings`, `/hub` — `DASHBOARD_PATHS`, `isDashboardPath`), checked by its own bundler-world tsconfig (includes `.tsx`). It is styled with StyleX on `@syneva/design-system` (no Tailwind): styles live in colocated `*.styles.ts` next to their module, markers and variables in `*.stylex.ts`, and since class names are hashed, DOM hooks are ids and data attributes, never classes. The build gathers every entry's CSS imports and StyleX rules into one stylesheet, `styles.css` (plus the font files under `fonts/`), which each page shell links and the hub serves (`STATIC_PATHS.styles`, `STATIC_PATHS.fontsPrefix`); global CSS is therefore limited to the font faces and zero-specificity rules scoped under one page's root attribute. The desk's own scales, night theme and scoped CSS are documented in `DESIGN.md`.
- `apps/landing` (`@syneva/landing`): the public site at syneva.dev, a static Astro app styled with StyleX and laid out in Feature-Sliced Design layers like the frontend. It is not part of the published package. Read `apps/landing/AGENTS.md` before touching it, `packages/design-system` or `packages/motion`.
- `packages/design-system` (`@syneva/design-system`): the design system every front shares (the site and the hub UI) — StyleX tokens, themes, breakpoints, control recipes, the mark and the self-hosted fonts — consumed as source; its `README.md` lists the exports. `packages/motion` (`@syneva/motion`): the public site's motion runtime (on Motion), consumed as source by `apps/landing`.

Core and local are ESM NodeNext, checked and compiled by `tsc` to their own `dist/` (which `test/benchmarks/guide-partition.mjs` imports), and export `./*` the way contracts does: `types` and `@syneva/source` on the TypeScript source, `default` on `dist/*.js`. Local imports core as `@syneva/core/<layer>/<module>` (no extension: the export map adds it): the type-check reads core's source as a library (neither emitted nor under local's `rootDir`), a build or an install runs core's `dist/` (turbo's `^build` builds it first), and the dev loop its source.

Turbo task graph (`turbo.json`): `build` (`dependsOn ^build` and `transit`, outputs `dist/**`) and `check` (same dependencies) run per package, where `transit` is a no-op task that folds source-only workspace dependencies (`@syneva/design-system`, `@syneva/motion`) into the hash; root `package.json` scripts delegate (`build`/`check` → `turbo run …`) while `lint`/`lint:types`/`format`/`format:check` stay repo-wide oxlint/oxfmt runs from the root. `pnpm dev` builds nothing: `apps/syneva/scripts/dev.ts` runs the hub from source under `node --watch` (tsx as the loader) and passes it a Vite dev server as its `UiServer` (core's `http/ui-server.ts`; an install serves the built bundle through local's `adapters/inbound/http/routes/static.ts`), so the UI loads from source with HMR on the hub's own origin and URLs, and the `@syneva/source` export condition resolves `@syneva/contracts` to its TypeScript in both worlds, `@syneva/core` and `@syneva/local` to theirs in the hub. A core, local or contracts edit restarts the hub (desks restore), a frontend edit hot-reloads. The dev hub is the machine's hub (port 4747, `~/.syneva`): stop an installed one first (`syneva hub stop`).

## Two compilation worlds

The review app splits the same way: a Node side (`packages/core/src/**` and `packages/local/src/**`, ESM NodeNext — imports inside a package use `.js` extensions, local reaches core through `@syneva/core/*`) and a browser frontend (`packages/frontend/src/**`, React 19). The two worlds never import each other at runtime: `packages/contracts/src/` (`review.ts`, `browser.ts`, `agent.ts`, `hub.ts`, `routes.ts`, `spec.ts`, and `bridge.ts`: the frames, paths, limits and close codes of the hub's push path) is the single source of truth for the shared wire shapes (core's persisted shapes live in `packages/core/src/domain/review.ts`), and the frontend entities map contract DTOs into frontend-owned models at their `entities/*/api.ts` boundaries — change a wire type in `packages/contracts/src/` alone. Core's layers, strictly downward (`http` → `hub` → `application` → `domain`): `domain` (pure review/diff/guide/identity rules, no IO), `application` (use cases, DTO mappers, cache/mutation ownership, and `ports.ts`, the ports every IO goes through: `open-desk.ts` builds a desk's review, `desk-summary.ts` projects it for the dashboard, `journal.ts` is the hub journal: what happened on the hub, recorded when it happens and served as `GET /api/hub/journal`; `plan-library.ts` is the hub's plan library: every plan desk's versions and approvals, posted from its desk's events and kept under `~/.syneva/hub/plans`, served as `GET /api/hub/plans`), `hub` (`hub.ts` is the registry of live desk contexts, `context.ts` one desk's context, `hosted-desk.ts` wires one desk: its context and the journal binding that names it on every event; `hub-signals.ts` is behind `hub.subscribe()`, the one source every push transport reads: what moved, when it moves; `stream-queue.ts` and `stream-frames.ts` turn those signals into one stream's frames (the snapshot, the coalescing per desk, the journal batches) and `stream-rate.ts` is a socket's inbound budget, all timer-free so a Durable Object reads them as the local stream does) and `http` (on the Fetch API: `router.ts` is the one request entry point, taking a `Request` (and its channel: `direct`, or `relayed-over-pairing` for a request the probe dispatches, which skips the Host/Origin and access guards and nothing else) and handing back a `Served` — `exchange.ts`: the `Response` plus the `afterSent` work that must follow it, never a socket hook —, `auth.ts` the access key, `routes/` the desk routes, `ui-server.ts` the port the UI bundle is served through). Local's: `adapters/{inbound/{cli,http,pi},outbound/{git,filesystem,source,editor,package-registry,console,bridge}}` (transport and IO: `outbound/source` outlines a file through `oxc-parser` (TS/JS) or its Markdown headings, so every changed block is named by the declaration it sits in (core's `application/change-symbols.ts`, read in one `git cat-file --batch`); `inbound/http/local-server.ts` serves core's router under node:http through `inbound/http/node-adapter.ts`, laying the parked `await-send` (`inbound/http/routes/await-send.ts`) over core's desk routes, and serves the hub's stream, `GET /api/hub/ws`, over `ws` on the server's `upgrade` event (`inbound/http/stream/`: the upgrade passes core's `upgradeRefusal`, the guards every route passes, then one stream per socket, whose timers are its coalescer and its silence bound); `inbound/cli/hub-client.ts` is how the CLI finds and auto-starts the hub), and `bootstrap` (composition roots: `hub.ts` starts the hub and hands core its ports, `cli.ts` is the entry the published bundle starts from).

The frontend follows Feature-Sliced Design with layer aliases (`@app/*`, `@pages/*`, `@widgets/*`, `@features/*`, `@entities/*`, `@shared/*` — declared in `packages/frontend/tsconfig.json`, wired in `vite.config.ts`, and oxlint's layer rules); the wire shapes come from the `@syneva/contracts` package, not an alias. The layers, strictly downward: `app` (bootstrap, the reactive store and its bindings facade, hotkeys, the desk's follower of the hub's stream — `desk-stream.ts`, loaded after the first paint: its desk's `pulse` frames, its presence in the listing, the stream's state mirrored into the store for the covers — global shell, `index.html`; `dashboard.tsx`/`dashboard.html` is the hub dashboard's own root), `pages` (`desk` — `overview.ts` is a desk view mode, not a separate page — and `dashboard`, the hub's application: its overview in three displays of the same desks — the circuit, the board, the cockpit — then reviews, projects, plans, settings and the hub page, routed in the page by `shared/lib/router.ts`), `widgets` (`diff-view`, `chrome`, `dialogs`, and `hub-shell`: the hub's sidebar, the dashboard's frame and the desk's rail, which the desk loads after its first paint), `features` (`decide-change`, `manage-comment`, `send-review`, `expand-context`, `open-editor`), `entities` (`review` — one review aggregate including its change/comment/guide/file segments — plus `settings` and `hub`, whose slice holds the stream: `stream.ts` is the page's one store of what the hub's WebSocket said — its hello, the desks, their pulses, the journal deduplicated by `(hubId, seq)`, the plans — opened by its first reader and closed with its last, a snapshot replacing it whole at `snapshot-end`; `useHub`, `useJournal`, `usePlans`, `usePlan` and the desk tab all read it, and `link.ts` says how the hub answers (`HubStatus`); the turn model and the journal live there too), and `shared` (API transport — HTTP, and the hub's stream in `shared/api/stream.ts`: one socket, RFC 0001's close-code policy and backoff, the ping and its pong — UI/lib primitives, markdown, the generic diff renderer/highlighting infra, icons, and the hub's motion runtime: `shared/lib/motion.ts` and its hooks, the Web Animations API on the design system's curves, no dependency). The desk's API calls are prefixed with the desk's base (`/api/desks/<id>`, read once from the page URL in `shared/api/base.ts`); hub routes are absolute. Composition happens above: same-layer slices don't import each other's internals, lower layers never import `app`, and the imperative render path reaches the funnel only through the narrow scheduler seam (`@shared/lib/render-scheduler`). Only the entity API boundary modules (`entities/*/api.ts`) name HTTP paths — always via `@syneva/contracts/routes` — and decode contract DTOs into the frontend-owned models (`entities/review/decode.ts` mapping onto `entities/review/model.ts`); the stream's payloads decode at the same kind of boundary (`entities/hub/stream.ts`, `entities/review/pulse.ts`). No frontend code re-asks the hub on a timer: the timers left are the transport's ping, pong deadline and retry wait, the display clock (`shared/lib/use-now.ts`, only while a reader is on a shown page), the saver's settle limit, and UI timing (toasts, focus hand-offs, tooltips, go-to-line, the close notice); a read the hub left unanswered tries again when the hub next answers, never on a timer: on its next hello, or on the first frame of its stream past the read's backoff, a deadline compared when the frame comes (`retryWhenHubAnswers` in `entities/hub/stream.ts`, on `shared/lib/answer-retry.ts`). The file diff renders directly through `@pierre/diffs` in `widgets/diff-view/diff-instance.ts`.

Lint/format behaviour is the shared `@nextnode-solutions/standards` preset; `oxlint.config.ts`/`oxfmt.config.ts` hold only repo-specific ignores and narrow overrides with a stated reason.

## Render path

All render passes funnel through `packages/frontend/src/pages/desk/render.ts`; `widgets/diff-view/diff-instance.ts` keeps one `FileDiff` per file on screen and calls `render()` again on every pass, following `@pierre/diffs`' own model: Pierre skips what did not change, so the inputs must keep their identity while unchanged — the diff metadata is memoized (`diff-metadata.ts`, a fresh object re-tokenizes the file), annotations reuse their objects and array (`stable-annotations.ts`, a fresh one rebuilds the rows), every option callback is a stable function, and option changes go through `setOptions`/`setThemeType`. The diff header is our own DOM, refilled each pass (`file-header.ts`). Following Pierre's surface choice, a very large file (over 3000 lines on its longer side, e.g. one opened with "Load diff anyway") renders as a `VirtualizedFileDiff` through a `Virtualizer` on `#diff`, so only the rows around the viewport are mounted; the cursor's jumps, go-to-line and the overview ruler then fall back on Pierre's line layout (`getLinePosition`, `widgets/diff-view/virtual-nav.ts`) for rows that are not mounted. Every other file keeps a full render (and the browser's find). Tokenizing never runs on the main thread: every instance highlights through Pierre's worker pool (`diff-workers.ts`, booted by `app/main.tsx` with the first file's grammar), which paints plain rows at once and caches highlighted results under the metadata's content `cacheKey` — the next file is primed into that cache ahead of the step (`diff-prime.ts`, via `app/facade/navigate.ts`). The theme and line-diff mode the pool highlights with are pushed with `setRenderOptions`, not through the instance options. `packages/frontend/scripts/bundle-budget.mjs` budgets the whole static import graph, not just `ui.js`. `@pierre/diffs` renumbers lines per render — display anchors are derived, raw file lines stay canonical.

## Key invariants

- `Decision` records (keyed `path:stableKey`) — not git staging and not the rendered diff — are the source of truth for accept/reject. They survive reloads even when accepting staged the hunk out of the working-tree diff.
- `contentHash`/`reviewedHash` pairs detect staleness: if the agent rewrites a block (or a file) after it was decided/approved, the decision/approval resets to pending on reload. The same pattern invalidates comment anchors (`anchorText` → re-anchoring → `unanchored`) and guides (`baseDiffHash`).
- A guided desk always has a guide: every open, restore and reload drafts the code no explained domain owns (`domain/guide-redraft.ts`; deterministic, grouped by the changed declarations and the references between them in `domain/guide-partition.ts`), and a posted guide is laid over the current one (`domain/guide-compose.ts`): a domain it leaves out keeps its words and its staleness. `guideResolution.drafted` lists the domains no agent has explained; after every open and reload the CLI writes the agent's guide.json and one code packet per pending domain from `GET /authoring` (`application/guide-authoring.ts`). No model runs in any of it.
- Desks are idempotent per repo+session: `deskId` hashes repo root + session, so a second open reuses (reloads) the live desk and the same `/d/<id>/` URL survives a hub restart (the hub registry under `~/.syneva/hub/desks.json` records every desk's rebuild parameters; `restore` rebuilds them on start). The hub never closes a desk on its own. The hub lock (`~/.syneva/hub/hub.json`) is trusted only if its pid is alive AND the hub answers `/api/hub/health`.
- The hub binds one fixed port (4747) and is itself idempotent: a second `start` finds the live hub and exits 0; the CLI auto-starts a detached hub when a desk command finds none. Binding beyond loopback requires an access key (`--key`), checked as a Bearer header or a signed-in cookie; the Host/Origin guard stays on in every mode.
- The hub journal (`~/.syneva/hub/journal.jsonl`, `application/journal.ts`) records an event when the thing happens (a desk opened, reloaded or closed, a round sent or picked up, a question asked, an agent's reply), never derived later from desk state. A failed write never fails the request that recorded it, an event joins the served tail only once it is on disk, and a `seq` is never handed out twice, across restarts too. A hub restart restores desks without recording anything.
- The hub pushes: `hub.subscribe()` (`hub/hub-signals.ts`) signals synchronously at every point that moves what a tab shows (a desk opened, reloaded or restored, a state commit, its status, events, activity or liveness, a closure, a journal event once on disk, a plan write). A listener only notes the signal and never reads the desk then: a stream projects its frames when it sends them, so a burst sends a desk's latest `desk` and `pulse` once per `coalesceMs`, and an unchanged one not at all. A throwing listener never fails the mutation that signalled (logged once). The local stream (`GET /api/hub/ws`) subscribes before it reads its snapshot (`hello`, each desk's `desk` and `pulse`, the journal tail, the plans, `snapshot-end`), takes every bound and close code from `BRIDGE_LIMITS`/`CLOSE_CODES` (`contracts/bridge.ts`), never sends a frame over `frameBytes` (core shapes a pulse that would pass it partial: its head and a digest of the rest, which the tab reads whole at `GET …/pulse` when the digest moves), closes a socket silent past `silenceMs` (its tab pings every `pingIntervalMs`) with `silent` and a reader that left more than `bufferedBytes` unread with `slow` (live frames start once the snapshot is written out), and closes its sockets with `goingAway` when the hub stops; a reader deduplicates journal events by `(hubId, seq)`. `test/stream/conformance.mjs` checks it frame by frame against a scratch hub. The polled routes (`/poll`, `/api/hub/desks`, `/api/hub/journal`, `/api/hub/plans`) still answer the same payloads; the browser no longer reads them.
- A paired hub pushes to the web too. `syneva login` pairs the hub with the web by a device code (`inbound/cli/login.ts`, the one polling loop of the pairing, commented: before the CLI holds a token the web has no way back to it) and leaves `~/.syneva/hub/bridge.json` (0600); `syneva logout` revokes the token and removes it, and both tell the running hub (`POST /api/hub/bridge/reconnect`, loopback only, never relayed). A hub with no `bridge.json` opens no socket. A paired one runs the probe (`outbound/bridge/`, composed in `bootstrap/bridge.ts`): one outbound WebSocket carrying the local stream's frames from core's same stream queue, every id the web's: the hub by its 16-hex web hub id, a desk or a plan by `<hubId><localId>` (`webDeskId` in `contracts/bridge.ts`; journal seqs untouched), paced under the bridge's inbound budget (`send-window.ts`), kept open by the client policy (`policy.ts`), its state pushed to the hub's own tabs as `pairing` frames (the Hub page). The web's relayed requests are answered in process (`relay.ts`): a path `contracts/relay.ts` does not list, that does not read as itself, or that names another hub's desk is refused before the router; the rest run on the router's `relayed-over-pairing` channel, so a relayed action does exactly what a local tab's does. Its timers: the wait before the next attempt, the link's ping and pong deadline, the outbox's wait for room in the window, and the coalescer's (`adapters/stream-pacer.ts`, one per socket, as on the local stream). `test/bridge/conformance.mjs` checks it against a fake bridge (`test/bridge/README.md`): run it after any change to the probe, the pairing, the relay or the stream.
- `packages/core/src/application/state-cache.ts` caches the serialized browser response per review revision: `DeskContext.serialize` invalidates around mutations, and the cache must never be keyed solely on `baseDiffHash`.

## Hub smoke

There is no unit suite, so the hub is verified end to end by hand: build, then start a hub on a spare port with a scratch `HOME`, open a repo desk from a temp git repo (`syneva open --no-open`), drive `await`/`comment`/`status`/`reload`/`close` against it and read the journal those leave (`GET /api/hub/journal`) and the dashboard pages (`/`, `/reviews`, `/projects/<id>`), stop and restart the hub to see the desk restored, and start one with `--key` to check the 401/login paths. Keep that loop green after any change to the hub, the CLI or the desk routes.

## Conventions

- Commits follow **Conventional Commits** (`feat:`, `fix:`, `perf:`, `refactor:`, `docs:`, `chore:`, …); `semantic-release` (config in `apps/syneva/.releaserc.json`, extending the shared `@nextnode-solutions/standards` preset) infers the semver bump from the prefix, publishes the `syneva` package and cuts the GitHub release. Run it with `pnpm release`; don't edit the version by hand.
- Comments in this codebase explain *why* and record invariants; match that style.
- Polling is a last resort, never an architectural choice. Whichever side is waiting (a browser tab, the CLI, the hub, a Worker) subscribes to a push path first — a stream (SSE, WebSocket), a request the server parks and the event resolves, a subscription on the thing that changes — and re-asks on a timer only when no such path exists at all. A polling loop that survives that test carries a comment naming the push path it stands in for and why it was ruled out. The hub pushes; its UI and its agents listen.

## Serverless cost discipline (`apps/web`)

The web service is a stateless Worker plus one Durable Object per user, `UserHub`, with two roles: core's hub over the web adapters for web desks (RFC 3.4, mode 2) and a switchboard of hibernating WebSockets for paired hubs (RFC 4, mode 3). Its bill stays bounded only while these rules hold; `docs/rfc/0001-core-web-local.md` (section 6) catalogues every way it can run away, with numbers, guards, detection and the test that proves each guard.

- Two roles, one discipline. As the switchboard for paired hubs the object is never a store: it forwards frames between a user's hubs and tabs, holds nothing across wakes, never touches `ctx.storage` (the paired hub is the truth; a snapshot is requested from it on every tab connect and on every wake that needs one), and sets a socket's attachment once, at accept. As the user's web hub it writes per action only (a decision, a comment, a reload, a posted guide), never per frame, restores lazily (the registry first, a desk only when a route names it), and reloads on GitHub webhooks, never on a timer.
- Nothing may keep an object awake: only `ctx.acceptWebSocket()` (never `ws.accept()`), no timers anywhere in the bundle (core is timer-free by lint: grace periods and TTLs are deadlines compared on the next read), no alarms, no outbound I/O in the switchboard role (`fetch`, stubs, email and D1 belong to the Worker) and in the hub role only the GitHub adapter's calls, each with a 10 s deadline and a size cap, no streaming or long-lived response other than the bounded HTTP relay (30 s deadline, 1 MiB frames, 32 MiB per response, 32 in flight per object), and never a parked request: an agent's long wait on a web desk is a hibernating socket. Pings are a `setWebSocketAutoResponse` pair, so they never wake it and are never billed.
- Every socket is rate limited inside the object (close `1008` above 100 frames/s or 2 MiB/s) and capped in number (8 hubs, 32 tabs per user, close `1013` beyond); every public path is rate limited at the edge (one WAF rule) and refused by the Worker, before any object is touched, when unauthenticated; `limits.cpu_ms` stays set on the Worker.
- No per-frame logging anywhere; invocation logs off (`invocation_logs = false`), lines sampled (`head_sampling_rate` at most 0.01) and emitted on connect, close and error of accepted sockets only (a refused request writes nothing); no Logpush, no tail Worker, no Analytics Engine, no KV, no cron.
- Clients (the probe and the frontend transport) reconnect with exponential backoff and full jitter (1 s to 60 s), honour the close codes (`1008` rate: 30 s, `1013` too many: 60 s, `4001` revoked: stop, `4029` saturated: 5 min) and send one ping every 30 s; they never retry a relayed action on their own.
- Budget detection is not this repo's: control-center's budget agent reads the Analytics API hourly against the RFC's thresholds (6.4) and trips the breaker through the Worker's ops route (`4029` on upgrades, every object drained, relays `503`), or blocks the hostname at the edge when Worker requests run away; `apps/web` ships the thresholds and the route, never a canary. A deploy drops every socket: deploy at low traffic, never more than once a day.
- One Cloudflare account, the Paid plan, no Free tier: zero means every billable dimension has a hard bound (RFC 6.6) and nothing is paid for nothing, not a plan that fails operations at a cap.
