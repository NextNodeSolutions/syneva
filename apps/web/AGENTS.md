# apps/web

Guidance for coding agents working on `@syneva/web`, the web side of RFC 0001 (`docs/rfc/0001-core-web-local.md`), phase 2. Read the root `AGENTS.md` first (its "Serverless cost discipline" section is the contract this package is held to), then the RFC's sections 4 (the bridge), 6 (the serverless horror catalogue) and 8 (contract, schema, config).

## What this is

A Cloudflare Worker and one Durable Object per account, `UserHub`. The RFC gives the object two roles: core's hub over web adapters for web desks (3.4, mode 2, phase 3) and a switchboard of hibernating WebSockets for paired local hubs (4, mode 3). **Only the switchboard exists in this phase.** The object holds a person's hub sockets and tab sockets, forwards each hub's live stream to every tab and a tab's snapshot to that tab alone, and carries the HTTP relay between a tab's request and a hub's answer; it stores nothing. The Worker in front of it signs people in (magic link), pairs hubs (device code), serves the frontend's page shells and bundle (static assets), answers the identity routes from D1, and is the only caller of the object. No model runs here either.

## Layout

- `src/worker.ts` — the entry: the route order below, the one catch-all log line, and the `UserHub` export wrangler binds.
- `src/bridge/**` — the object, and nothing else: `user-hub.ts` (the class: its internal routes, the socket handlers), `switchboard.ts` (what a hub frame does, what a closed socket leaves), `sockets.ts` (attachments, tags, the sockets open now, quiet sends and closes), `relay.ts` (one relay: the only module with a stream), `relays.ts` (the relays in flight), `frames.ts` (a hub frame read once), `buckets.ts` (a hub socket's inbound budget), `internal.ts` (the Worker → object protocol: paths, headers, shapes; the one module both sides import).
- `src/user-hub-stub.ts` — the Worker's half of `internal.ts`: every object call, each a request the Worker builds itself.
- `src/auth/**` — sessions (`session.ts`), the magic link (`magic-link.ts`, `follow-link.ts`, `mail.ts`), pairing (`pairing.ts`, `device-token.ts` for the CLI; `device.ts`, `device-answer.ts`, `device-view.ts` and `approval-proof.ts` for the person), the rate limiter (`limits.ts`), secrets and codes (`secrets.ts`).
- `src/routes/**` — ops and the breaker (`ops.ts`, `saturated.ts`), the hub's socket (`hub-socket.ts`), what a session opens (`session-routes.ts`, `settings.ts`, `relay.ts`), the health probe, the page shells.
- `src/pages/**` — the server-rendered pages (sign-in, device, sign-out, not found), on core's page shell styles.
- `src/db/**` — one module per D1 table, and `session-reads.ts`, the session read with what a route opens in one statement; `migrations/` the schema, one additive file per change (`0001_identity.sql` the first).
- `src/http/**` — the request (`call.ts`), answers and the error shape (`answer.ts`), bodies under a cap (`body.ts`), a Bearer token (`bearer.ts`), the same-origin guard (`guard.ts`), the statuses (`status.ts`), the one log boundary (`log.ts`).
- `scripts/build.mjs` (tsdown bundles `src/worker.ts` into `dist/server/entry.mjs`, contracts inlined, `cloudflare:workers` external; the frontend's `dist` copied to `dist/client`, its two HTML files moved under `_shell/`), `scripts/bundle-check.mjs` (run by `build`).
- `ops/thresholds.json` — RFC 6.4's thresholds, handed to control-center.

## Who a limit counts

`auth/client-keys.ts` reads `cf-connecting-ip` into two keys. The **client** is an IPv4 address or an IPv6 /64: a device holds a whole /64 (SLAAC, rotating privacy addresses, a VPS's allocation), so an IPv6 address alone is a key anyone can change at will; every spelling of a prefix is one key, and an IPv4-mapped address is its IPv4 address. The **network** is an IPv4 address or an IPv6 /48, what a site or a free tunnel broker hands out. RL_AUTH's sign-in and pairing budgets and the hourly per-client link cap count clients; the day's links count networks too (`link_networks`, 50 each), so draining the 2,000 a day takes forty networks, not one client rotating addresses. The share is per network, not a reserve kept for known accounts: a reserve would answer an address with an account differently from one without, and `/auth/magic-link` answers 202 alike.

## Request order (R9)

`src/worker.ts` runs its routes in the security order: each refuses before it reads more than it must, and nothing reaches an object before the caller is known.

1. **Ops** (`POST /bridge/v1/ops/breaker`, `POST /bridge/v1/ops/drain`, `GET /bridge/v1/ops/status`): `OPS_TOKEN` as a Bearer, compared in constant time (`crypto.subtle.timingSafeEqual` on digests), else 403 with nothing read. Tripping writes the breaker row, then drains the first page of the people's objects (`/drain`, six at a time, one request per user, at most 100 a call) and answers the page's `next`; the ops caller follows it with `POST /bridge/v1/ops/drain { after: next }` until `next` is null (409 `NOT_TRIPPED` once cleared, 400 on a cursor or size that does not read); clearing stamps `cleared_at`. The contract, for control-center: `packages/contracts/src/ops.ts`.
2. **Sign-in and the device page**: `GET /login`, `POST /auth/magic-link` (RL_AUTH per client, then 3 links per address and 10 per client an hour, 50 per network and 2,000 in all a day in D1; the user row is created when the link is taken), `GET /auth/callback` (reads only: a page naming the account, its button the POST), `POST /auth/callback` (same-origin: the token taken once, the session opened), `GET`/`POST /logout` (the POST's `next` is where sign-in lands after), `GET`/`POST /device` (a session, same-origin, RL_AUTH per person; the page names the hub and the signed-in account with a "not you?" sign-out back to the code, and its Approve carries a proof, an HMAC of the session's digest and the code under `SESSION_SECRET`, without which an approval is 403 `DEVICE_UNCONFIRMED`).
3. **Pairing and the hub's socket**: `POST /bridge/v1/device/code` (RL_AUTH per client), `POST /bridge/v1/device/token` (the interval and an attempt count bound it, never RL_AUTH; the ask that takes an approved code draws the token and writes the hub's row with its sha256, in one transaction), `DELETE /bridge/v1/hub` (the hub's token), `GET /bridge/v1/ws` (the hub's token by digest, RL_AUTH per hub, the breaker, then `/hub`; one `last_seen_at` write, after the answer and only for a socket the object accepted, at the time it accepted it).
4. **`GET /api/hub/health`**: the shape a local hub answers.
5. **Everything else under `/api/`**: the same-origin guard (Host, then Origin on a mutation or an upgrade), then one D1 read with the session in it (401 when it opens nothing, before anything else is looked at): the account's routes read it alone (`/api/web/me`, `/api/web/hubs` and `DELETE /api/web/hubs/<id>`, `/api/hub/settings` and a desk's `/api/desks/<webId>/settings`, the same D1 document, never relayed: the web keeps the person's preferences, and a machine's settings.json, which names the editor command its hub runs, is not the web's to write); the tab's socket `/api/hub/ws` reads it with the person's hubs and the breaker (`db/session-reads.ts`), then RL_TABS per person (429), the breaker (503), and only then the upgrade (426 for a plain GET, which a tab sends to learn why an upgrade failed, so it meets every refusal first), then `/tab`; and last the relay reads it with the hub it names and the breaker, then checks `isRelayable`, the hub (named by the web id's prefix or `x-syneva-hub`, the person's own), the body under 1 MiB, the breaker, then `/relay` under a 30 s deadline (past it, `/cancel/<id>` and 504). One round trip each, where the relay took three.
6. **Page shells**: a dashboard path or `/d/<webId>/` with a session cookie present gets its shell from the assets (`/_shell/dashboard`, `/_shell/desk`); without one, a redirect to `/login?next=`. Anything else: 404, a page for a navigation, JSON otherwise.

## The object's rules, and what holds each

| Rule (RFC 6.3) | Held by |
|---|---|
| R1 `ctx.acceptWebSocket` only, never `ws.accept()` | `eslint/no-restricted-properties` (`accept`) in `src/bridge/**` |
| R2 no timer, alarm, `waitUntil` or `blockConcurrencyWhile` | `eslint/no-restricted-globals` (the timers, `queueMicrotask`) and `no-restricted-properties` (`setAlarm`, `waitUntil`, `blockConcurrencyWhile`) in `src/bridge/**`; the timers banned in all of `src/**`; `scripts/bundle-check.mjs` greps the bundle for `setTimeout(`, `setInterval(`, `.setAlarm(` |
| R3 no outbound I/O | `no-restricted-globals` (`fetch`) and `no-restricted-imports` (only `@syneva/contracts`, `cloudflare:workers` and `./*`) in `src/bridge/**` |
| R4 no `ctx.storage`; the attachment set once, at accept | `no-restricted-properties` (`storage`); `bundle-check.mjs` greps `ctx.storage`; `serializeAttachment` appears in the two accepts only |
| R5 the only stream is `relay.ts` | `no-restricted-globals` (`ReadableStream`, `WritableStream`, `TransformStream`) in `src/bridge/**` except `relay.ts` |
| R6 rates per socket, caps per person, tabs send pings only | `BRIDGE_LIMITS` (`buckets.ts`: 100 frames/s, 2 MiB/s, close 1008; 8 hubs and 32 tabs connected, the next upgrade refused with 409, `TOO_MANY_STATUS`: see the deviations; a tab's non-ping frame, close 1003) |
| R7 the auto-response pair is the constructor's only work | `user-hub.ts`'s constructor; code review |
| R8 no per-frame log; `console.error` only on a socket's error | `eslint/no-console` (`allow: ['error']`) in `src/bridge/**`; `http/log.ts` is the Worker's one line; `observability` in `wrangler.jsonc` |
| R9 the Worker authenticates before any object call, bounds bodies, keeps `cpu_ms = 50` | the route order above; `http/body.ts`; `wrangler.jsonc` |
| R12 the bundle is contracts and the web's own code | `scripts/bundle-check.mjs` fails on any import but `cloudflare:workers`; `no-restricted-imports` bans `@syneva/local` and `@syneva/frontend` in `src/**` |

Two more invariants the code keeps: the Worker builds every object request from scratch (`user-hub-stub.ts`), so no client header named like an internal one (`x-syneva-object-*`) ever reaches the object; and a hub's stream frame reaches the tabs as the hub's own text, never re-encoded, once its hub id is the socket's (another hub's id closes it with 1008). A connecting tab's `snapshot?` carries that tab's socket id as its `tag`, and the hub echoes it on every frame of that snapshot: a tagged frame goes to the tab its tag names (`tab:<socket id>`), to none once it closed, so a connect never resends the person's other tabs a snapshot they hold (6.1 B10); an untagged one, the live stream or a hub before tags, to every tab; a tag that does not read (not text, empty, past `snapshotTagChars`) closes the socket with 1003, as any frame that does not read.

The web's own pages (sign-in, sign-out, the device page, not found) go out under one policy (`pages/shell.ts`'s `pagePolicy`, sent by `http/answer.ts`'s `html`): `default-src 'none'`, the page's one inline sheet by its sha256 (no other style, no script at all), the faces from the assets, `form-action 'self'`, `frame-ancestors 'none'`, `base-uri 'none'`, plus `x-frame-options: DENY`, `nosniff` and `referrer-policy: no-referrer` (a sign-in link's token never leaves in a `Referer`). The frontend's shells get `frame-ancestors 'none'`, `DENY` and `nosniff` (`routes/shells.ts`): their own policy is the frontend's, but no other site frames a page whose buttons act on a machine. Every JSON answer is `nosniff`.

## D1

`migrations/0001_identity.sql`: users, sessions (the cookie's HMAC under `SESSION_SECRET`), login codes (a token's sha256, its address, `next`, the client's sha256), device codes (the device code's sha256, the user code, the account and hub id once approved), hubs (written when the CLI takes its approved code, with the token's sha256: the token itself is never stored, `0003_token_never_stored.sql`; `last_seen_at` written when its socket opens, never per frame; a revoked hub keeps its row), user settings, the breaker row, the daily email counter; `0002_link_networks.sql`: the day's links per network (its sha256); `0003_token_never_stored.sql`: device codes lose the parked token and gain `taken_at`. A change is a new file, never an edit of an applied one. Timestamps are ISO strings. Expired rows are purged on the next write to the same table, never on a timer (no cron): device codes on every write the table gets (a code asked for, an ask counted, an approval, a denial, a take).

## Local loop

```sh
pnpm build                                     # contracts, frontend, then this package
cd apps/web
printf 'SESSION_SECRET=%s\nOPS_TOKEN=%s\n' "$(openssl rand -hex 32)" "$(openssl rand -hex 32)" > .dev.vars
pnpm db:local                                  # applies migrations/ to the local D1 under .wrangler/
pnpm dev                                       # wrangler dev (Miniflare) on http://127.0.0.1:8787
```

`.dev.vars` and `.wrangler/` are gitignored. With `MAIL_TRANSPORT=log` (the default in `wrangler.jsonc`'s vars) the magic link is printed on wrangler's stdout as `{"event":"magic-link","link":"..."}`; set `MAIL_TRANSPORT=resend` and a real `RESEND_API_KEY` in `.dev.vars` and it is sent from `hello@syneva.dev`. Pair a local hub with `syneva login --web http://127.0.0.1:8787` (the hub runs on the same machine: give it a scratch `HOME` and port, never the machine's hub). `wrangler dev` is the only runtime here: never `wrangler deploy`, `wrangler login` or `--remote`.

## Smoke

`node test/web/smoke.mjs` (after `pnpm build`) runs the whole loop against `wrangler dev` with a scratch D1, a scratch local hub and the CLI: sign-in, pairing, the tab's socket, the relay, revocation, logout, the connected cap, the breaker, sign-out. `test/web/README.md` says what each check means; `node test/bridge/conformance.mjs` stays the probe's own check.

`node test/web/cost/run.mjs` (after `pnpm build`) runs the cost acceptance tests of RFC 6.7, T1 to T10, with fake hubs against `wrangler dev`: floods and caps (T2), relay bounds (T4), concurrent streams (T5), the breaker (T6), and the parts of T1, T3 and T7 to T10 that need no edge or Analytics API as a dry run. What only a deployed Worker settles (the objects' active time, the Worker's request count, the edge rule, logs) the runner drives against `--staging <origin>` and prints as numbered reads for a person; `test/web/README.md` ("Cost tests") has the flags, the inputs and what each test checks. T1 runs again on staging on every change to `src/bridge/**`.

## Deviations from the RFC

- **Breaker refusals** (6.5): an upgrade is refused with HTTP 503 `SATURATED`, not close code 4029, since a close code needs an accepted socket, which is an object call; clients read a 503 on an upgrade as "wait five minutes" (4.3), like 4029. A relay answers 503 `HUB_OFFLINE`, as 6.5 says. The drain reaches every user's object, not only those of the hubs seen in the last day (a tab may be open with no hub online), a page of at most 100 per ops call: one call draining every object would outgrow a Worker invocation as the users grow, and a call cut short could not go on. The page is a range of user ids, the cursor the last one drained; nothing is queued or scheduled (no cron, no alarm), the ops caller asks for each page, and asks a failed one again with the same cursor (a drained object drains again for nothing).
- **Lint** (6.3): oxlint has no `no-restricted-syntax`; R1, R2 and R4 are held by `no-restricted-properties` on the property names instead.
- **Log lines** (R8): `console.error` on a socket's error only, not on every close (a close is normal operation).
- **R12**: the bundle is contracts only; core and the web adapters join it with the hub role (phase 3).
- **Relayed answers** keep a header allowlist (`content-type`, `cache-control`, `etag`, `last-modified`, `content-disposition`, `vary`), never a cookie, and gain `content-security-policy: default-src 'none'; sandbox` and `x-content-type-options: nosniff`: a hub's bytes (a `/blob` SVG) are served on the web's origin.
- **Relay bounds inside the object**: a reader slower than two chunks cuts the relay (no buffering past ~1.1 MiB a relay); a relay the Worker never cancelled is dropped at twice the deadline, compared on the object's next event.
- **A relay that fails after its head** (a hub streaming past `responseBytes`, which a probe never does, 4.5 step 3; or a hub socket closing mid-answer) ends as a cut body after its 200, not the 413 or 502 of 6.7's T4: the head goes out with the hub's first frame, and a status that waited for the size or the end would hold the answer whole (R5). The 413 is the probe's own `err TOO_LARGE`, sent before any head; the 502 a hub socket closing before its head. T4 checks all four, the 413 with the real hub.
- **T5 runs scaled on `wrangler dev`** (6.7): 8 relays of 8 MiB, byte-exact; `--full` is the RFC's 32 of 32 MiB, for staging, where a relay may end whole or cut. A hub socket carries 2 MiB/s and an account at most 8 hubs, so 32 answers of 32 MiB cannot finish within the 30 s deadline (they would need 4 MiB/s a hub), and `wrangler dev` has no memory limit to exceed nor an `exceededMemory` count to read: the full shape proves nothing locally.
- **The relay's deadline** bounds the whole exchange from the Worker's side; `/cancel/<id>` goes only when no answer started (a body cut mid-stream reaches the object as its reader leaving, which cancels the hub's side).
- **The hub's token** (4.2) is drawn when the CLI takes its approved code, not at the approval, so it is never parked in D1 between the two; the hub's row is written then.
- **The tab's upgrade** is rate limited per person on its own binding, `RL_TABS`, sixty a minute: RL_AUTH's ten would refuse a person's tabs reconnecting together after a deploy (B4, up to 32), and sixty still bound a reconnect loop to one a second.
- **Additions**: a cap of 32 hubs per account at approval, paired or approved and not yet taken (409 `TOO_MANY_HUBS`; 8 of them connect at once, `hubsPerUser`, since a paired machine is often off), a hub's name cut to 64 characters (it rides each tab's upgrade to the object), RL_AUTH on the hub's upgrade per hub, a per-client hourly cap on sign-in links and a per-network daily one (a client an IPv6 /64, a network a /48: "Who a limit counts"), a 64 KiB cap on settings, `GET /logout` as a confirmation page (the sign-out itself is a same-origin POST), the sign-in link likewise (its GET a page naming the account, which a mail scanner can fetch at will; the session opened by the page's same-origin POST, whose tries the five follows count), a page shell handed over on a cookie that merely looks present (no D1 read per navigation; its first API call says 401).
- **The `hub` frame's `lastSeenAt`** is when the hub last connected (the row's `last_seen_at`), for an offline hub too: the object writes nothing on close (6.3 R3).
- **The connected caps** (6.3 R6): past 8 hubs or 32 tabs connected, the object accepts no socket and answers the upgrade 409 (`TOO_MANY_STATUS`; the Worker says it in its error shape, `TOO_MANY_HUBS` or `TOO_MANY_TABS`), not an accepted socket closed with 1013. Under workerd (wrangler dev) a close the object issues as it accepts a socket never reaches the client: it reads the socket open, then nothing, not even a pong, so a refused hub called itself connected until its pong deadline. The probe waits 60 s after a 409, as after 1013, and its Hub page and `syneva login` say "too many hubs connected on this account"; a browser's WebSocket reads no status, so a tab past its cap backs off as after any refused upgrade. A refused hub costs one object request, no socket and no D1 write: the object answers an accepted socket with when it accepted it (`x-syneva-object-connected-at`, never handed on), which the Worker writes as `last_seen_at` after the answer, so a hub refused every minute never reads as connected. At each refusal the open tabs get that hub's `hub` frame, offline, with `refusedAt`; the object keeps none of it, and a tab that connects later reads the hub plainly offline until its next refusal.

## Deploy: what the pipeline must learn

Nothing here deploys yet, and nothing should from a machine. `NextNodeSolutions/core`'s `deploy.yml` builds a Worker's config from `nextnode.toml`, and the root `nextnode.toml` describes the landing only: do not add this service there until the pipeline can emit the fields below. What it must learn to deploy `apps/web` (staging first, RFC 6.6: same account, its own D1 and objects):

- **A Durable Object binding and its migration**, as `wrangler.jsonc` has them: `durable_objects.bindings = [{ name = "USER_HUB", class_name = "UserHub" }]` and `migrations = [{ tag = "v1", new_sqlite_classes = ["UserHub"] }]` (TOML: `[[durable_objects.bindings]]` and `[[migrations]]`). The class is exported by the entry (`dist/server/entry.mjs`).
- **Observability**: `observability.enabled = true`, `observability.head_sampling_rate = 0.01`, `observability.logs.enabled = true`, `observability.logs.head_sampling_rate = 0.01`, `observability.logs.invocation_logs = false`, `observability.traces.enabled = false` (R8; RFC 6.1 D1, D5).
- **A D1 database and a migrations folder per service**: this one's `DB` binding on its own database (never the landing's), `migrations_dir = "apps/web/migrations"`, applied before each deploy as the landing's are.
- **`limits.cpu_ms = 50`**, `workers_dev = false`, the rate limiters `RL_AUTH` (`simple = { limit = 10, period = 60 }`) and `RL_TABS` (`simple = { limit = 60, period = 60 }`, its own `namespace_id`), and the assets block: `directory = "apps/web/dist/client"`, `binding = "ASSETS"`, `not_found_handling = "none"`, optionally `run_worker_first` with the Worker's routes (`/api/*`, `/bridge/*`, `/auth/*`, `/d/*`, `/login`, `/logout`, `/device`) so a route never matches an asset first; the Worker is correct without it (the shells sit under `/_shell/`).
- **Vars and secrets**: `SITE_URL` (the app's origin), no `MAIL_TRANSPORT`; `SESSION_SECRET`, `OPS_TOKEN` and `RESEND_API_KEY` from the `syneva` Infisical project, synced like the landing's.
- **The zone** (R10, 6.6): one WAF rate limiting rule on the app hostname and Bot Fight Mode on, checked by the deploy smoke; control-center gets `OPS_TOKEN` and `ops/thresholds.json`.

Deploy at low traffic, never more than once a day: a deploy drops every socket (RFC 6.1 G1).
