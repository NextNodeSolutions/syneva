# Deploy the landing

The landing's development and production workflows use the shared NextNode deploy pipeline. Both start by manual dispatch. Production requires a successful landing development run for the same commit. The Worker serves Astro's built pages and the signup endpoint. [Landing config](../apps/landing/nextnode.toml) · [Development workflow](../.github/workflows/deploy-landing-dev.yml) · [Production workflow](../.github/workflows/deploy-landing-prod.yml)

## Verify ownership before the first production deploy

1. In Cloudflare, record the apex DNS and custom domain or route, the active Worker and deployment version IDs, their traffic shares, and the deployment timestamp and source. Read the `DB` binding from the active version and record the D1 database ID. A public `/healthz` response confirms availability only. The [October 6 archive run](https://github.com/NextNodeSolutions/syneva-archive/actions/runs/37514439829) deployed `syneva-landing-production-web` and ran migrations for `syneva-landing-production-d1`. Use those names to locate the resources and the active version to confirm what serves today.
2. In HCP Terraform, open `syneva-landing-production` in the organization used by CI. Verify Local execution mode and compare its current `cloudflare_d1_database.d1` resource and `d1_database_id` output with the active Worker's binding. Check for other workspaces or automations that can modify the database or deploy the same Worker. Terraform owns D1. Wrangler manages the Worker and its custom domain through CI.
3. On that database, use read-only queries to check the `d1_migrations` ledger and the `subscribers` schema, including `reminded_at`. Compare the ledger with the committed migrations and confirm that a recovery point is available. Keep subscriber data out of evidence and logs. CI applies only pending files in the ledger. A manually added column with no ledger entry can still make the migration fail. [Migration files](../apps/landing/migrations/)
4. Stop if the apex target, D1 ID, or ownership differs. If the expected database is already at the current state address, reuse it. If it is outside that state, the infrastructure owner must reconcile ownership and adopt the existing ID at that address through an approved state operation before retrying. Review the resulting plan for D1 creation, replacement, or deletion and stop on any of those actions. If the apex points to another target, agree on the domain transfer and how to restore the prior target before enabling rollout.

## Promote the verified commit

1. Verify that Syneva can use `INFISICAL_IDENTITY_ID`, `INFISICAL_PROJECT_ID`, and `TF_CLOUD_ORGANIZATION` in Actions. Verify the CI identity's OIDC trust for core and its access to `nextnode-ci/main` and `syneva/dev` and `syneva/prod`. Confirm `RESEND_API_KEY` by name in each application environment. Review the shared project before granting deploy access because core syncs its application keys into each scripted Worker. [Core vault setup](https://github.com/NextNodeSolutions/core/blob/main/packages/infrastructure/README.md#vault-setup)
2. After approval for development resources and access, dispatch **Deploy landing development** and check its `/healthz`, static pages, and signup with an approved development address in the development database. Keep the Actions run and commit SHA.
3. After production ownership, recovery, and deployment approval are confirmed, dispatch **Deploy landing production** for that SHA and check `/healthz` and a static page. Read back the active deployment and versions and confirm the apex and D1 ID still match. Record the Actions run, commit SHA, Worker version IDs, and health result together.

## Roll back

For a code regression, revert the faulty release in Git and deploy the revert through the same development and production workflows. Check that the reverted Worker can read and write the current D1 schema. A Worker rollback leaves D1 migrations and subsequent signups in place.

If the normal release cannot restore service in time, an authorized Cloudflare operator can restore the recorded Worker version after verifying that its bindings and schema still work. If the hostname moved during cutover, restore its recorded prior target under the approved route restoration plan. Recheck `/healthz`, the serving version, and the database binding. Treat D1 recovery as a separate incident. Restoring a snapshot over the current database can discard signups received after the snapshot. [Cloudflare Worker rollback](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)
