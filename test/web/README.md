# The web's smoke

`node test/web/smoke.mjs` checks `apps/web` end to end, locally: its built Worker under `wrangler dev` (Miniflare; nothing touches a Cloudflare account), a scratch local hub started from the CLI build, and the CLI itself. Build first (`pnpm build`), then:

```sh
TMPDIR=<a scratch directory> node test/web/smoke.mjs [--web-port 47984] [--port 47983] [--spare-port 47985] [--cli apps/syneva/dist/cli.js]
```

Everything it writes goes under one directory in `os.tmpdir()` (set `TMPDIR` to keep it out of `/tmp`): the D1 and object state (`--persist-to`), wrangler's logs and config, the hub's `HOME` (its `~/.syneva`, its `bridge.json`), the second hub's (`spare-home`, for the connected cap), the scratch git repo. The three ports must be free (it checks and stops otherwise); it never touches the machine's hub on 4747. The secrets are drawn per run and passed as `--var`, with `MAIL_TRANSPORT=log`, so the sign-in link is read from wrangler's stdout.

One line per check, `ok` or `FAIL` with what was seen; the count at the end; exit 1 on any failure, the scratch directory kept and named.

## What it checks, in order

- **Signed out**: `/api/hub/health` answers a hub's health (no key, no desk); `/` and a dashboard page redirect to sign in; `/api/web/me` is 401; a tab's upgrade is refused 401; the ops status without its token is 403; the sign-in and not-found pages carry the pages' policy (`default-src 'none'`, `style-src` naming the sha256 of the very sheet the page holds, no `script-src`, `frame-ancestors 'none'`, `x-frame-options: DENY`, `nosniff`, `referrer-policy: no-referrer`).
- **Sign-in**: `POST /auth/magic-link` is 202; the link printed opens a page that names the account, under the pages' policy, and spends nothing (twice 200, no cookie); another site's POST of its token is 403; the page's same-origin POST opens a session (303 to `next`, an `HttpOnly`, `SameSite=Lax` cookie); posted or opened again, the link lands on `/login?expired=1`; `/api/web/me` names the person; a dashboard page serves its shell; settings round-trip; a cross-site POST is 403; the sign-out page carries the pages' policy and keeps its `next` and a dashboard shell `frame-ancestors 'none'`, `DENY`, `nosniff`.
- **Who the limits count**: speaking from documentation addresses through `cf-connecting-ip` (wrangler dev passes it on), ten links from one IPv6 /64 in ten spellings, then 429; each other /64 of the /48 gets its own ten until the /48's fifty for the day, then a fresh /64 is refused; another /48 still gets its link; an IPv4 address and its IPv4-mapped spelling are one client, its neighbour another; device codes are limited per /64 too.
- **Pairing**: `syneva login --web <web> --no-open` prints a code and the device page; the page shows the hub, names the signed-in account with a "not you?" sign-out back to the code, and is under the pages' policy; an approval without the page's proof, or with a forged one, is 403 `DEVICE_UNCONFIRMED`; `POST /device` with the proof approves it; the CLI exits 0 once the hub is connected; `bridge.json` holds a 16-hex hub id; the code pairs once (410); the code is spent and the hub's row holds the token's sha256 (read with `wrangler d1 execute --local`); the token's bytes are in no file of the web's local state, D1's database and WAL included, where an address is (the control).
- **The tab's socket**: it opens; a `hub` frame says the hub is online with its version and last connect; the hub's `hello` (its web id) and `snapshot-end` follow; `/api/web/hubs` lists it online.
- **A second tab's snapshot**: a second tab of the same person opens and reads the hub's snapshot, every frame of it, `hello` to `snapshot-end`, carrying one tag; the tab already open reads none of it; a desk opened and closed through the relay reaches both tabs, untagged.
- **The relay**: the machine opens a desk on a scratch repo first (`syneva open`: a relayed open names a root the hub serves), then `POST /api/hub/desks` with `x-syneva-hub` opens another desk there, named by its web id, and the tab reads its `desk` frame and `desk-opened`; the desk's `/state` answers through the relay, sandboxed (CSP, `nosniff`); the desk's `/settings` is the account's D1 document, written under the desk's web id and read back there and at `/api/hub/settings`, never relayed (the local hub's own settings are unchanged), and under an id that does not read is 404 `NOT_RELAYED`; a comment shows in the tab's `pulse`; a question's `question-asked` reaches the tab and the hub's own journal (by the local id); a session that opens nothing is 401 before its hub is looked at (the session and the hub are one read); `/poll` is 404 `NOT_RELAYED`, another hub's web id and a missing header 404 `HUB_NOT_FOUND`, a body over 1 MiB 413.
- **Revoke from the web**: `DELETE /api/web/hubs/<id>`; the tab reads the hub offline; the hub's own stream says its link stopped, `revoked` (close 4001); the hub is no longer listed.
- **Logout**: `syneva logout` exits 0 (the token is already revoked: it says so) and removes `bridge.json`.
- **A second account**: it signs in; its tab's plain GET of `/api/hub/ws` passes the guards and hears 426, sixty times (RL_TABS), then 429 `RATE_LIMITED`, and its upgrade is refused 429 too, while the first account's still opens (below).
- **The connected caps**: a third account pairs eight hubs over HTTP (each from its own /64) and opens their sockets, each read online by its tab; a ninth, a running hub paired with `syneva login` and approved with the page's form (the page it answers says up to 8 hubs connect at once), is refused at the upgrade: login exits 0 saying it could not connect yet, too many hubs connected on this account (HTTP 409); its own Hub page reads that in backoff; a raw upgrade with its token is 409 `TOO_MANY_HUBS` in the error shape; the tab reads it offline with a `refusedAt`, never online; `/api/web/hubs` lists the eight online with a last connect and the ninth offline with none (a refused upgrade writes nothing). One of the eight leaves: the ninth connects on its next attempt (online on the tab, connected on its Hub page), and only then does its row hold a last connect. Then its tabs: with 32 open, the next upgrade is 409 `TOO_MANY_TABS` in the error shape; one closed, the next opens.
- **The breaker**: the ops status with the token (three users); tripping it with a page of one drains the first object and answers a `next`, `POST /bridge/v1/ops/drain` with it drains the last (`next` null), a cursor or size that does not read is 400, the drain without the token 403, and the open tab closes with 4029; a tab's upgrade is then refused 503, and a relay to a live hub of the person's (paired over HTTP alone, never connected) is 503 `HUB_OFFLINE` for the load shed; cleared, it opens again, and a drain is 409 `NOT_TRIPPED`.
- **Sign-out**: `POST /logout` clears the cookie, 303 to `/login` carrying its `next` (as the device page's "not you?" posts it); the old cookie opens nothing.

## Cost tests

`node test/web/cost/run.mjs` runs the cost acceptance tests of RFC 0001, section 6.7 (T1 to T10): what keeps a Durable Object awake, what a hostile or broken peer can make it do, and what a deploy or the breaker does to the clients. The smoke checks that the web works; these check that it stays cheap. They need no hub from the CLI: the hubs are fake ones (`test/web/cost/fakes/`) that pair like a real one (a device code approved with the account's cookie, a token asked once) and then misbehave on request: flood, send an oversized or malformed frame, never answer a `req`, stream N MiB, drop mid-answer.

```sh
pnpm build
TMPDIR=<a scratch directory> node test/web/cost/run.mjs [--only T2,T4] [--web-port 47994] [--inspector-port <port>] [--port 47993] [--cli apps/syneva/dist/cli.js]
                                                       [--minutes <n>] [--hubs <n>] [--tabs <n>] [--seconds <n>] [--full] [--restart] [--procedures]
                                                       [--allow-unmeasured]
```

It starts one `wrangler dev` (as the smoke does: a scratch D1 and object state, secrets drawn per run, nothing touches a Cloudflare account; `--inspector-port` pins the devtools port it opens beside `--web-port`, 9229 or the next free one otherwise), signs the accounts it needs in through the magic link on wrangler's stdout, pairs fake hubs as they are first used, runs the selected tests and prints one `ok` or `FAIL` line per check. On a failure it also prints the Worker's own log lines that look like a fault, and keeps the scratch directory. A test that only a deployed Worker can settle runs its local dry run, or prints `skip (staging)`; a skip is never an `ok`. Neither is a reading the runner could not take (no local Explorer answered, or the Explorer lost what it was to count): it is a `FAIL measured: <what>`, unless `--allow-unmeasured` makes the run a dry run that goes without it (`unmeasured <what>`). The summary names every reading not taken and, against `--staging`, the tests whose reads are left to a person. `--port` and `--cli` are accepted for symmetry with the smoke; no test needs a real hub yet (`test/bridge/conformance.mjs` is the real probe's, including its own `err TOO_LARGE`).

| Test | Where | Locally | On staging (`--staging`) |
|---|---|---|---|
| **T1** hibernation proof | staging | 8 hubs and 8 tabs held `--minutes 2` with pings only: every socket open, no frame but the pong reaches any of them, every ping answered, the Worker not invoked, and `wrangler dev`'s log shows no event run in the object (plus one real frame afterwards that does, so the check is not blind) | 50 hubs and 50 tabs for 30 min (`--hubs`, `--tabs`, `--minutes`), the same checks, then the Analytics read of the objects' active time (< 5 s) |
| **T2** flood | local | 1,000 frames/s closed `1008` within a second; 3 frames of 900 KiB closed `1008`; another hub's id `1008`; a frame over `frameBytes`, text that is no frame, a binary frame, an object-only kind `1003`; a tab's text or binary frame `1003`, its ping answered; the 9th hub and the 33rd tab `1013`; after each, the other sockets are open | the same against the Worker, then the Analytics read (< 2 s for the flood minute) |
| **T3** reconnect storm | staging | 100 upgrades in a second with a bad token and 100 with no session: all 401, no object created or woken, no log line; a known hub reconnecting 30 times in a loop is held to ten by RL_AUTH | 100 connects a second for `--seconds 60`: the rate rule's first 429 within 10 s (a 403 is another rule, and does not count), the attempts that reached the Worker under 1,000; then the Worker-request read and the edge-event read |
| **T4** relay bounds | local | a 40 MiB answer cut at `responseBytes` with `cancel` sent to the hub; a hub that never answers: 504 `HUB_TIMEOUT` at 30 s +/- 2 and `cancel`; the 33rd concurrent relay 429; `err TOO_LARGE` 413; a hub closing before or mid-answer; no hub socket: 503 in under 50 ms beyond a request the Worker refuses itself (medians of 20 pairs, so a client far from a deployed Worker times the Worker, not the network) | the same, the cut body must then be a read error; then the read of the object's idle time |
| **T5** memory | local | 8 relays of 8 MiB, one per hub, sha256 byte-exact, every socket open | `--full`: 32 relays of 32 MiB (see below), no `exceededMemoryErrors` |
| **T6** breaker, app stage | local | wrong or missing `OPS_TOKEN` 403 and nothing touched; trip: tabs and hub `4029`, relay 503, both upgrades 503; clear: everyone is back and the tab reads its `hub` frame | the same (it trips the staging breaker: needs `--ops-token`) |
| **T7** deploy drill | staging | `--restart` restarts `wrangler dev` under 5 tabs and a hub: all back within 60 s, at most 8 attempts each, none faster than its backoff step, none dropping again | the clients watch while you deploy a no-op change; same checks |
| **T8** log volume | staging | what the Worker's own code wrote during a hold (stdout and the dev log table, the runtime's entries aside): nothing | the hold is `--minutes 60`; the Workers Logs count read (< 100) |
| **T9** free pages | staging | 50 loads each of `/ui.js`, `/dashboard.js`, `/styles.css`, a font (assets' headers, 304 on `If-None-Match`) and of `/`, `/reviews`, `/d/<id>/` (the shell, `no-store`); the Worker's invocations that started in the window, per path: the 150 shell requests and no asset request (a round counts only when the Explorer recorded every shell load, three rounds at most) | the same loads, then the invocation read against asset requests |
| **T10** breaker, edge stage | staging | `skip (staging)`; `--procedures` prints the steps | the WAF rule's API steps, a trace of 5 tabs: refused at the edge, at most one attempt per client per 5 min, all back within the window once the rule is deleted |

`--staging <origin>` runs the tests marked staging (or those `--only` names) against a deployed Worker, with the inputs only a person has: `--cookie` (the `syneva_session` cookie of a signed-in account, once per account: the caps are per person, 8 hubs and 32 tabs, so T1 at 50 and 50 needs seven; `--cookie` is read in order) and `--ops-token` (never printed, never committed). Each test prints the reads it cannot make itself as a numbered list under `reads for T<n>`: the GraphQL Analytics API's queries (the object's active time, the object's and the Worker's requests, the edge's firewall events) and the Workers Logs count, with the window to read and the number to expect. The dataset and field names are those documented when this was written; verify them by introspection first. Metrics lag: read ten minutes after the run. Pairing is paced by the rate limiter (ten codes a minute per address and per person), so T1 at full size spends minutes opening its fleet before the hold starts.

T1 again on every change to the object's code (`apps/web/src/bridge/**`), on staging.

What the local run cannot show, and why the staging read stays:

- **Billing.** `wrangler dev` has no active time. What it can show is that nothing wakes the object: its log records every event the object's code runs, and a ping run by the auto-response is none.
- **Asset requests.** `wrangler dev` prints a request line for an asset as for a page, so its stdout cannot tell them apart (T9); its local Explorer records a request line for each Worker invocation and none for an asset. It is a lossy instrument: an upgrade's invocation is recorded when its socket ends (so every count is of the invocations that started inside the window), and its collector drops records when it falls behind (37 of 150 shell loads after the other tests), so T9 paces its loads to what it records and takes a round as evidence only when every shell load is there.
- **A cut relay body.** On a deployed Worker the body of a cut relay errors in the tab; `wrangler dev`'s proxy ends any aborted stream with the normal terminator, a plain Worker's own errored stream included. Locally T4 checks the cut by the bytes that arrived; on staging it requires the error.
- **A refused socket's close.** The over-the-cap `1013` is delivered at once, but `wrangler dev` holds the TCP close back ten seconds; the fakes time the close frame, as a browser acts on it.
- **T5 at full size.** A hub socket carries 2 MiB/s and a person has at most 8 hubs, so 32 answers of 32 MiB cannot finish inside the Worker's 30 s deadline (they would need 4 MiB/s a hub). `--full` therefore requires only that each relay ends whole and byte-exact or cut, and that the object and its sockets live: the memory is what is being tested.
- **The clients' policy.** T7 and T10 keep their sockets with the probe's policy module (`packages/local`). The frontend's own transport (`shared/api/stream.ts`) follows the same RFC 4.3 waits: five minutes after an upgrade refused with 403, 429 or 503, so a tab behind the edge rule retries once in five minutes, as a probe does.

The probe's own behaviour against a web-like peer is `test/bridge/conformance.mjs`.
